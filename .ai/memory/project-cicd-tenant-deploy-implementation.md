**Fact:** As of July 2026, "Use Case 1" from the CD initiative's chart-onboarding automation work — upgrading an existing chart's version, tenant-wise — is built and validated end-to-end on real infrastructure (devops site, `gitconnect` tenant). This was previously a confirmed gap (`.bump_env` only ever touched the site-level `apps.yaml`; `.deploy_env` never looped tenant folders at all — zero tenant discovery, zero tenant deploy).

**What changed, in both repos:**
- `cim-solution` (`CX-5.4.0`, branch `CRM-763-factory-loop-test`, MR !638 into `5.4.0_f-CRM-765`): `.bump_env`'s per-file bump logic is factored into `bump_apps_file()` and now runs once for the site-level `apps.yaml` and once per `sites/<site>/tenants/<tenant>/apps.yaml` — one bump commit still advances site + all tenants atomically (CD plan §3.6 item 2, now actually implemented, not just designed).
- `cx-environments-cd` (branch `CRM-782-sites-tenants-restructure`, MR !1): `.deploy_env`'s per-chart deploy logic is factored into `deploy_one_chart()` and reused for both the existing site-level loop and a new tenant loop over `sites/<site>/tenants/*/apps.yaml`. No separate "prepare the namespace" step was needed or built — `--create-namespace` (already present on every `helm upgrade --install`) handles it for free. Cross-namespace secret/cert propagation into a tenant namespace stays deliberately manual/deferred, same class of gap as devops's already-accepted Vault/Postgres/Mongo dynamic-creds gaps.

**Real bugs found and fixed while validating against live infra (not hypothetical):**
1. **Helm release names must be lowercase (RFC 1123 label); chart names aren't.** First attempt used the raw chart name as the tenant release name (`REL="$name"`) — broke immediately on `MTT-single` (`Error: release name is invalid: MTT-single`). **Fix, confirmed against the actual deployment guide's own command** (`helm upgrade --install ... <tenant-id> --values ... expertflow/MTT-single`): the release name is the **tenant id itself**, not derived from the chart name at all. This only holds because each tenant runs exactly one tenant-scoped chart (`MTT-single` — literally named "single" for this reason); a second tenant-scoped chart type would collide on this release name and need its own scheme.
2. **Vault's Helm chart bakes `.Chart.Version` into the pod template's own labels** (`vault/templates/server-statefulset.yaml:38`, `helm.sh/chart: {{ template "vault.chart" . }}`, inside `spec.template.metadata.labels`, not just the StatefulSet's top-level labels). This means **any** Chart.yaml version bump — even a pure RC-number bump with zero real content changes, exactly what `package_charts`' auto-bump does — changes the pod template hash and forces Kubernetes to roll a new Vault pod. A new pod always starts sealed (seal state is in-memory, not on disk) — **unsealing is required after every single vault chart deploy, regardless of whether anything meaningful actually changed.** Not a bug in our pipeline, just a fact to plan around: it's a restart, not a re-init (existing `vault-init-keys.txt` unseal keys still work, storage persists).
3. **`MTT-single` has real local subchart dependencies** (`conversation-studio`, `campaign-studio`, `qm-connector`, `qm-backend`, etc., each `file://charts/...`) that are raw chart source, not packaged `.tgz`. Manually packaging it for a one-off registry push requires `helm dependency update` first, or the parent package bundles stale/empty dependency archives.

**Process note confirming an existing gotcha:** `detect_charts` diffs the MR's merge-base cumulatively, not "since last run" — a stale early-session commit (`1ea132a0`, "touch 12 devops-scope charts to drive first factory publish") kept resurfacing as "changed" on every `CRM-763-factory-loop-test` pipeline run for the rest of this session, including re-bumping Vault (see #2) every time. Harmless but noisy; only resolved by merging the MR or cleaning up that commit.

**How to apply:** If a new tenant-scoped chart type is ever added, do NOT reuse "release = tenant id" unless it remains true that each tenant runs only one tenant-scoped chart — check this assumption first. If touching Vault's chart for any reason, expect and plan for a reseal step afterward, every time.
