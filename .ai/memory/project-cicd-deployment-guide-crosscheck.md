**Fact:** July 2026 — `cx-environments-cd/.deploy_env`'s per-chart namespace/release-name/extra-flags `case` statement was cross-checked line-by-line against the official Confluence **"(5.6.0) Deployment Guide"** (space CX, page id 2177925196) — its own documented `helm upgrade --install` commands are the authoritative source, not the pipeline's prior assumptions.

**Real bugs found and fixed, not hypothetical:**
- **`agent-desk`'s release name was wrong for the entire test phase**: pipeline used `REL="$name"` ("agent-desk"), guide says `cx-agent-desk`. Never caught by pod-health checks — pods came up fine regardless, because pod health doesn't prove a release name used for service-to-service lookups is correct. Only caught by deliberately reading the guide's own command for a *different* chart (`channels`) and then auditing the rest defensively.
- `channels` → `cx-channels`, `campaigns` → `cx-campaigns`, `reporting` → `cx-reporting`: none of these were in the `case` statement at all before; they were silently falling through the generic catch-all with the wrong (un-prefixed) release name.
- `clamav` was wrongly grouped with `minio|redis|apisix` (no extra flags); guide shows it needs `--set global.efCxReleaseName=$CORE_RELEASE` like every other CX-suite chart.
- `fluent-bit` was falling through the catch-all into the `expertflow` namespace with release `fluent-bit`; guide shows it belongs in `ef-external` with release `cx-fluent-bit`.
- Confirmed correct (no change needed): `eleveo-middleware`, `middleware-cronjob`, `cisco-sync-service`, `cisco-connector` (all un-prefixed release names, matches guide).
- **Not resolved, flagged for later**: the guide's own `reporting` command uses a `<tenant-namespace>` placeholder, suggesting Reporting Scheduler may need to be tenant-scoped like MTT-single rather than pinned site-level (currently still pinned site-level on RMT) — a bigger structural question, deliberately not touched in this pass.
- **`expertflow-ai`, `redis-thirdparty`, `secure-link-generation`, `transflux`** are NOT documented in the current 5.6.0 guide at all (only a stale 4.8-era ETL page exists for transflux, not trustworthy for current conventions) — still relying on the unverified generic catch-all for these; explicitly flagged as unverified in the code's own comments now, not silently assumed safe.
- Also found (unrelated, pre-existing): `middleware-cronjob`'s `Chart.yaml` `name:` field has a literal trailing space (`"middleware-cronjob "`), which silently breaks exact-string-match pin comparisons — a real latent bug in the chart source itself, not yet fixed, would cause every future bump of that chart to look "new" incorrectly.

**Phase 1 go-live scope decision (stakeholder-directed, same session):** externals (`postgresql`, `mongodb`, `redis`, `minio`, `apisix`, `keycloak`, `clamav`, `fluent-bit`) and **Vault** are explicitly EXCLUDED from this pipeline's Phase 1 scope — treated as prerequisites a site is expected to already have running/configured, not something `deploy:<site>` manages. `sites/devops/apps.yaml` and `sites/rmt/apps.yaml` were edited to drop all of these pins (plus `artemis`, already flagged separately as system-service-only) — commit `def3e1d` on `cx-environments-cd`'s `CRM-782-sites-tenants-restructure` branch. The now-unused `.deploy_env` `case` entries and `POSTGRES_PASS`/`REGISTRY_URL`/`REGISTRY_USER`/`REGISTRY_PASS` variables were deliberately **left in place, inert** rather than deleted — harmless since nothing pins those charts now, but preserves this guide-verified work for whenever Phase 2 re-expands scope to include externals. `transflux` stays pinned (it's expertflow-namespace tier, not an external).

**How to apply:** Never trust the generic catch-all's namespace/release-name guess for a chart without checking the Deployment Guide first — "it deployed and pods are healthy" is not evidence it's correct. When Phase 2 re-expands scope to externals/Vault, the case-statement work is already done and waiting, just currently unreachable since nothing pins those charts.
