**Fact:** July 2026 — design/discussion sessions (no `.gitlab-ci.yml` edited in any repo yet) worked through wiring Playwright test → notify onto `cx-environments-cd`'s deploy jobs. **Rollback is explicitly ON HOLD** (stakeholder call 2026-07-31) — test + notify only for this phase.

**Settled design (stakeholder-agreed 2026-07-31):**
- **`test` and `notify` move into `cx-environments-cd`**, lifted from `CX-5.4.0/.gitlab-ci.yml`'s `regression-test`/`notify-google-chat` pair. Those are **proven working** — cim-solution runs them with `PLAYWRIGHT_BRANCH = feature/ci-playwright-config` (NOT the `main` default baked into the file, which cannot work — see blocker below). `CX-5.4.0`'s copies get deleted once the new ones are green.
- **`include: project:` is REJECTED, not deferred.** It has **zero functional benefit here** — confirmed with the stakeholder. Because `include:` ships YAML and never files, the job must `git clone` the suite at runtime either way; runtime behaviour is byte-identical. All `include:` moves is where the job *definition text* lives. Costs it would have added: a `.gitlab-ci-template.yml` that doesn't exist (only needed *because* of `include:` — pointing at the QA repo's own `.gitlab-ci.yml` would drag in its `stages:` and two concrete jobs), plus cx-environments-cd's whole pipeline failing to *generate* (deploy jobs included) if the pinned ref ever stops resolving — a live risk since QA plans to merge and delete `feature/ci-playwright-config`. **Plan §5's premise was factually wrong:** it claims clone-and-run logic "exists in two places" including the QA repo's own pipeline — but that pipeline runs in its own checkout and clones nothing. There is exactly one clone-and-run implementation, and moving it keeps it at one.
- **One implementation, thin per-site stubs** — hidden `.regression_test` / `.notify_chat` holding all logic, with per-site jobs setting only `DEPLOY_ENV`/`environment:`, mirroring `.deploy_env` → `deploy:devops`/`deploy:rmt`.
- **Test scope is per-site, not per-tenant.** `BASE_URL` is a site-scoped CI/CD variable that happens to hold a tenant URL (e.g. `https://mtt02.expertflow.com`). Safe because `BASE_URL` is read at runtime in `script:` — unlike `rules:`, which is evaluated at pipeline-creation time before `environment:` exists (that trap killed the plan's env-scoped `RUN_REGRESSION` flag; **dropped — a site opts in by having a `test:<site>` job at all**).
- **`allow_failure: true` STAYS on the test job** (reverses an earlier recommendation). Stated purpose is notifying the team of the outcome either way; with no rollback consuming a hard failure, `false` buys nothing and would force edits to notify's proven `rules: when: on_success`. Cost accepted: the pipeline shows green when tests failed; the card carries the truth. **When rollback returns, flip `allow_failure: false` AND notify to `when: always` as one change.**
- **`notify:<site>` must `needs: [deploy:<site>, test:<site>]` with `when: always`** — NOT `when: always` on stage ordering alone. Both site's deploy jobs are manual buttons in every pipeline, so a stage-ordered notify would fire on a site whose deploy was never clicked and post a spurious card. Tying it to its own site's deploy is what makes a devops-only click leave rmt untouched.
- **`.deploy_env` gains an `after_script`** writing `DEPLOY_STATUS=$CI_JOB_STATUS` to a dotenv artifact (`when: always`), so the card can report deploy *and* test — which its title already claims. `CI_JOB_STATUS` is available in `after_script` and is exactly `success`/`failed`/`canceled`.
- **Notify clones the QA repo itself** rather than taking the script from the test job's artifacts — that dependency breaks precisely when deploy fails and test is skipped. Means notify's `alpine:3.20` image needs `git` added (currently only `jq curl`).
- Other port details: `npm ci` → `npm install` (matches the fix already made on the standalone pipeline in `ac200bd`; `npm ci` fails hard on any package.json/lockfile drift); drop the `before_script: []` override (it only existed to escape cim-solution's *global* `before_script`, which cx-environments-cd doesn't have); `environment:` with `action: verify`/`access` so test/notify don't register spurious deployments.

**MUST PROVE before relying on it:** whether `when: always` still fires when a needed job was **skipped** (not failed) — the deploy-fails → test-skipped → notify path. Verify on a throwaway pipeline. Fallback if it doesn't fire: post the deploy-failure card from `.deploy_env`'s own `after_script`, using the `DEPLOY_STATUS` dotenv already being added.

**Real bugs in the existing assets (fix as part of this work):**
- **`notify-google-chat.sh` mis-computes the pass count.** It sets `TOTAL=.stats.expected`, but in Playwright's JSON reporter `expected` is the *passed* count, not the total; then `PASSED=$((TOTAL - FAILED))`. Proven against the real `playwright-report/results.json` on disk (`expected:0, unexpected:1, skipped:9`): the card renders **"-1/0 passed, 1 failed"**. Correct: `TOTAL = expected + unexpected + skipped + flaky`, `PASSED = expected`. `flaky` is never surfaced at all. Card title also hardcodes "RMT Deployment + Regression" — needs a site variable.

**When rollback resumes (deferred, not designed away):** rollback granularity is *forced* to equal deploy granularity — `.deploy_env` redeploys every chart every run, so whole-site is the only coherent undo until the §3.6 marker lands. Mechanism must snapshot revisions *before* deploying (`helm list` → release/revision, or "absent") and roll back to recorded revisions, `helm uninstall`ing what was absent: a bare `helm rollback` means "back one", which overshoots when the inline per-chart rollback already fired, and fails outright on a first install (REVISION 1) — the live chart-onboarding path. Git state-revert must be path-scoped (`sites/<site>/` only), since one commit can touch two sites.
